Guia de integração

Autenticação para os usuários da sua aplicação

Toda aplicação cadastrada na Nexas ganha um módulo de autenticação pronto para os seus próprios usuários finais — cadastro, login, recuperação de senha, papéis (roles) e login com Google — isolado das demais aplicações e sem você precisar construir nada disso do zero.

Base URLhttps://SEU-AMBIENTE-NEXAS/api/
Formatoapplication/json
AutenticaçãoHeader X-Api-Key

i Visão geral

Pense nisso como o "provedor de identidade" da sua aplicação: você não guarda senha de ninguém, não implementa hash, e-mail de recuperação ou emissão de token — a Nexas cuida disso para os usuários finais do seu produto, do mesmo jeito que ela já faz isso para você mesmo (dono da aplicação) no portal.

O que você ganha

  • Cadastro e login por e-mail e senha, isolados por aplicação — o mesmo e-mail pode existir na sua aplicação e na de outro cliente Nexas como duas contas totalmente independentes.
  • Recuperação de senha por token, pronta para acoplar ao seu próprio fluxo de e-mail.
  • Papéis (roles) livres — Admin, Professor, Aluno, ou o que fizer sentido pro seu produto — com um usuário podendo acumular vários ao mesmo tempo.
  • Login com Google usando o Client ID OAuth da sua própria aplicação.
  • Um token JWT por sessão, pronto para o seu backend usar como prova de identidade nas próprias rotas.

Isso é diferente do seu próprio login no portal Nexas (onde você cadastra e gerencia a sua aplicação). Este guia é sobre os usuários do seu produto — os clientes do seu cliente.

1 Antes de começar

Você precisa de duas coisas do portal Nexas antes de escrever qualquer código.

  1. Cadastre (ou abra) sua aplicação em Aplicações no portal Nexas. Se ainda não tem uma, clique em "Nova aplicação" e preencha nome, domínio e descrição.
  2. Copie a Chave de API na página de detalhes da sua aplicação (card "Chave de API"). Ela identifica a sua aplicação em toda chamada aos endpoints deste guia — guarde-a com cuidado (veja a seção Segurança).

Se a chave vazar ou você suspeitar de uso indevido, gere uma nova a qualquer momento no mesmo card ("Gerar nova chave de API") — a antiga para de funcionar na hora.

2 Autenticação das requisições

Todo endpoint deste guia exige o header X-Api-Key com a chave da sua aplicação. Sem ele (ou com uma chave inválida), a resposta é sempre 401, sem corpo.

header obrigatório em toda chamada
X-Api-Key: nxs_sua_chave_aqui

Alguns endpoints (marcados abaixo) exigem além disso um token de sessão, enviado como Authorization: Bearer <token> — é o token que você recebe de volta no login.

Endpoints de referência

Todas as rotas abaixo têm como prefixo a base URL + v1/apps/auth.

POST /v1/apps/auth/google-login Autentica com uma conta Google
X-Api-Key

Cria a conta automaticamente no primeiro login (find-or-create por e-mail) — não precisa chamar /register antes.

Configuração (uma vez só, antes de usar)

  1. Crie um OAuth Client ID no Google Cloud Console, tipo "Aplicativo Web".
  2. Em "Origens JavaScript autorizadas", adicione o(s) domínio(s) de onde a sua aplicação roda (ex.: https://app.suaempresa.com.br).
  3. Copie o Client ID gerado (formato algo.apps.googleusercontent.com) e cole no card "Login com Google" da página de detalhes da sua aplicação, no portal Nexas.
  4. No seu próprio frontend, inicialize o Google Identity Services com esse mesmo Client ID e renderize o botão "Entrar com Google".
  5. Quando o Google devolver a credencial (response.credential), envie-a como idToken para este endpoint.
requisição
curl -X POST https://SEU-AMBIENTE-NEXAS/api/v1/apps/auth/google-login \
  -H "X-Api-Key: nxs_sua_chave_aqui" \
  -H "Content-Type: application/json" \
  -d '{"idToken":"<token que o Google devolveu no seu frontend>"}'

Resposta de sucesso é idêntica à do /login normal — mesmo formato de token e de usuário.

Erros possíveis

StatusCorpoQuando
400{"error":"Login com Google não está configurado para esta aplicação."}Você ainda não colou um Client ID no card "Login com Google" do portal.
400{"error":"Token do Google inválido."}Token expirado, assinatura inválida, ou emitido para um Client ID diferente do configurado.

Use o seu próprio Client ID do Google, nunca o da Nexas — cada aplicação valida contra o Client ID que ela mesma configurou, por isso o Google só aceita as origens que você autorizou no seu projeto.

POST /v1/apps/auth/forgot-password Inicia a recuperação de senha
X-Api-Key
requisição
curl -X POST https://SEU-AMBIENTE-NEXAS/api/v1/apps/auth/forgot-password \
  -H "X-Api-Key: nxs_sua_chave_aqui" \
  -H "Content-Type: application/json" \
  -d '{"email":"ana@exemplo.com"}'

Sempre responde 200 com corpo vazio, exista ou não o e-mail — por segurança, a API nunca revela se uma conta existe.

Nenhum e-mail é enviado automaticamente ainda — este endpoint só gera e guarda o token de redefinição. Enquanto o envio de e-mail transacional da Nexas não estiver disponível, você precisa do seu próprio canal (e-mail, WhatsApp, etc.) para entregar esse token ao usuário antes de chamar /reset-password. Fale com o time Nexas se precisar desse token de outra forma.

3 Papéis (roles)

Papéis são livres — você define quais fazem sentido para o seu produto (ex.: Admin, Professor, Aluno) e um usuário pode ter vários ao mesmo tempo.

Hoje, papéis são criados e atribuídos pelo portal Nexas (cards "Gerenciar papéis" e o ícone de editar ao lado de cada usuário, na página de detalhes da sua aplicação) — não há ainda um endpoint de API para o seu backend criar ou atribuir papéis programaticamente. O que a sua aplicação recebe é a leitura: os papéis já atribuídos aparecem no array roles das respostas de login//me e como claims dentro do próprio token.

Use isso no seu backend para autorização simples, por exemplo:

pseudocódigo
if (!usuario.roles.includes("Admin")) {
  return responder403("Sem permissão");
}

4 Estrutura do token JWT

O accessToken devolvido por login/google-login é um JWT assinado pela Nexas. As claims usam os nomes longos padrão do .NET — decodifique o payload (base64 da segunda parte do token) e procure por estas chaves exatas:

ClaimSignificado
http://schemas.xmlsoap.org/ws/2005/05/identity/claims/nameidentifierID do usuário (Guid)
http://schemas.xmlsoap.org/ws/2005/05/identity/claims/emailaddressE-mail do usuário
http://schemas.xmlsoap.org/ws/2005/05/identity/claims/nameNome completo (ausente se não informado)
http://schemas.microsoft.com/ws/2008/06/identity/claims/rolePapel(éis) — string única ou array, ausente se o usuário não tiver nenhum
app_idID da sua aplicação — sempre presente
token_typeSempre "app_end_user"
exp / iss / audExpiração, emissor e audiência padrão de JWT

Seu backend não tem a chave de assinatura — ela é privada da Nexas, de propósito, por segurança. Isso quer dizer que você não consegue validar a assinatura do token sozinho. Para confirmar que um token é válido e pertence à sua aplicação, chame GET /v1/apps/auth/me a cada requisição sensível — é rápido e já faz essa verificação (incluindo o isolamento entre aplicações) por você.

5 Referência de erros

StatusSignificado geral
400Dado inválido no corpo da requisição — veja o campo errors (ou error, no caso do Google) da resposta para o motivo exato.
401X-Api-Key ausente/inválida, credenciais de login erradas, ou token de sessão ausente/expirado.
403Token de sessão válido, mas de outra aplicação.

Observação: o formato do corpo de erro varia um pouco entre endpoints — a maioria usa o padrão problem+json do ASP.NET (campo errors, um dicionário por campo), mas /google-login usa um objeto simples { "error": "..." }. Trate ambos os formatos no seu client.

6 Exemplo de fluxo completo

Cadastro, login e uma chamada autenticada, em JavaScript puro (fetch).

javascript
const API_KEY = "nxs_sua_chave_aqui";
const BASE = "https://SEU-AMBIENTE-NEXAS/api/v1/apps/auth";

// 1. Cadastro
await fetch(`${BASE}/register`, {
  method: "POST",
  headers: { "X-Api-Key": API_KEY, "Content-Type": "application/json" },
  body: JSON.stringify({ email: "ana@exemplo.com", password: "SenhaForte@123", fullName: "Ana Silva" })
});

// 2. Login
const loginResp = await fetch(`${BASE}/login`, {
  method: "POST",
  headers: { "X-Api-Key": API_KEY, "Content-Type": "application/json" },
  body: JSON.stringify({ email: "ana@exemplo.com", password: "SenhaForte@123" })
});
const { accessToken, user } = await loginResp.json();

// 3. Guarde o token e use nas próximas chamadas ao SEU backend,
//    ou valide direto contra a Nexas quando precisar:
const me = await fetch(`${BASE}/me`, {
  headers: { "X-Api-Key": API_KEY, "Authorization": `Bearer ${accessToken}` }
});

7 Segurança

  • A chave de API identifica a sua aplicação, do mesmo jeito que a chave pública de um provedor de autenticação — mas ela permite cadastrar/autenticar usuários na sua aplicação, então trate-a como um segredo de produção mesmo assim: não a exponha em repositórios públicos.
  • Se for chamar estes endpoints diretamente do navegador do seu usuário final, isso é esperado (é como a própria Nexas usa a chave no seu portal) — mas se quiser uma camada extra de controle, você pode proxiar as chamadas pelo seu backend em vez do frontend.
  • Sempre use HTTPS em produção — senhas e tokens trafegam no corpo das requisições.
  • Se suspeitar de vazamento da chave, regenere-a no portal — a anterior para de funcionar imediatamente.
